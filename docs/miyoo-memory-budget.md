## 优化顺序与验收目标

以下数值是工程验收目标，不是原版硬件需求或代码已经强制实施的限制。
本轮模拟测试结果见下；实机完整流程仍需按这些条件复核。

1. **以实机余量和停顿为依据控制内存。** 统计进程 VmRSS/VmHWM、系统
   MemAvailable、进程 VmSwap 和系统 swap 相对启动基线的增量；60 MiB RSS、
   16 MiB 可用内存只保留为早期参考，不再作为固定验收线。以完整四人新局、
   开局动画、事件与面板切换、场景往返中的实际峰值和换页停顿判断工作集。
2. **资源按当前演出的实际使用期驻留。** 32 MiB 解码资源也只是早期工作预算，
   不设置会拒绝必要资源的硬上限。事件先匹配编号再加载；当前 FLC 的计时查询
   与绘制共享同一 lease。开局按 `0x415872` 保留所选角色的两组 JUMP 动画，
   装载在 loading 已显示时完成，避免查询帧数后释放、首帧再解压。
   活跃动画的差分状态不逐帧重建；不再使用的资源在后续帧回收，场景结束归还
   全部 lease。持续记录峰值，同时以顺序播放、音画时序和无换页长停顿为优先。
3. **以原版计时为帧节奏依据。** 普通地图行动慢／中／快为 120／80／40 ms
   一步；部分独立移动动画总周期为 24 ms；选人和退场定时器为 100／50 ms；
   FLC 使用资源头或调用 flags 指定的周期。绘图和提交计入周期，超时不再
   额外补一次固定等待。最快档地图更新、绘图及提交合计应在 40 ms 内，
   独立 24 ms 动画按各自预算验收；不能把全游戏统一改成 24 ms 或追求统一
   60 FPS。原版证据见 [计时与等待](evidence/render-cache-and-flc-state.md#原版计时与等待)。
4. **降低移动与不变画面的绘图成本。** 地面耗时较低的统计时段均值约
   0.64 ms，高耗时时段约 24.71 ms；后者整体约 13.3 FPS。须继续优化变化
   镜头的原有投影和采样。UI/覆盖层平均 11.64 ms，角色/物件平均 4.83 ms；
   按原版区域更新规则复用不变 HUD 与背景，保持文字、遮挡、透明和提交顺序。
   地面时段只是聚合报告分组，当前日志没有直接记录缓存命中次数。
5. **细分屏幕提交及长帧。** 当前 present 平均 14.65 ms，包含光标合成、
   RGB565 到 32-bit 转换、180 度旋转和 SDL_Flip，不能全部算作垂直同步。
   下一次实机诊断分别记录这些阶段，并增加 VmSwap、缺页及换入换出计数。
   资源 read_decode 同时包含文件访问和解压，也需要拆分后才能区分瓶颈。

装载优化以 21.35 秒和 123.58 MiB 为实测对照，分别比较首次所需资源字节数、
读取／解压及初始化耗时；Loading 必须先提交，再进行同步装载。FLC 继续保留
差分状态逐帧解码；本次 hits=1865、misses=48、rewinds=0，解码缓存峰值
2457600 bytes，不能再把每帧从头解码作为当前主要原因。

## 所有权与原版资源边界

当前 `ResourceStore` 支持 acquire/release lease，最后一个非永久 lease
释放即归还资源；全局未启用 LRU，掌机 `RICH4_RESOURCE_CACHE_MAX_BYTES`
实际为 0，不能将旧准备预算中的 16 MB 当作已执行的上限。
实现见 `src/resource/resource_store.c`、`src/platform/platform_profile.h`
和 `src/platform/sdl1/game_preview_assets.c`。

2026-10-15 IDA MCP 复核：`0x4190CF` 通过 `0x48A05C`（Panel.mkf）
装载通用界面资源 0–8，并不在这里装载全部面板；`0x418C55` 通过
`0x48A0E4`（Data.mkf）临时装载角色对应的 559+character，播放后立即释放。
拆分加载时沿这些已确认的调用边界逐组核对，保持原版显示和事件顺序。

## 验证

行为与像素回归继续使用 `test-render-equivalence`、`test-resource` 和
`test-miyoo-qemu`，全部经 `python scripts/make_minimal.py <target>` 执行。
耗时使用相同资源、人数、地图、速度档、音频和操作轨迹的实机对照，分别统计
静止地图、变化镜头、事件和 FLC；诊断开关保持一致，并报告平均值与长帧分位数。
保持逻辑时序、帧索引、像素和资源释放验证，不以删帧或减少效果满足目标。

## 本轮 128 MB 无交换验证

QEMU 实际 MemTotal 为 108772 KiB，SwapTotal 为 0。旧版同配置的新局、
地图和资源切换被 OOM 终止；保留在 `build/miyoo/demand-before128`。
新版完整结果在 `build/miyoo/qemu128`，对照在
`build/miyoo/demand-comparison.json`。

| 新版路径 | 进程 RSS 峰值 | 最低系统可用内存 |
| --- | --- | --- |
| 标题/设置 | 31.6 MiB | 58.4 MiB |
| 四人新局 | 50.0 MiB | 37.3 MiB |
| 双人地图 600 帧 | 51.3 MiB | 40.3 MiB |

这些路径的 VmSwap 均为 0；60/16 MiB 是当时的参考线。通用事件组合和实机
仍须继续验收，不能将一次回放视为完整游戏内存上界。
初始游戏资源缓存：四人 18.99 MiB（106 项），双人 17.61 MiB（98 项）。

旧版 128 MB 无法完成装载，故没有完整耗时可比。其相同二进制的 256 MB
完成结果作为单独标注的参考：四人装载 6070 ms，新版 128 MB 为 752 ms；
双人装载 6116 ms，新版为 694 ms。这不是同内存配置的速度基准。

同一 128 MB guest 中另跑无 smoke 参数的真实时钟标题对照：120 帧平均
总耗时 40.49 → 21.40 ms，平均等待 17.17 → 0.72 ms；新版还运行了
真实时钟的新局到地图路径。确定性回放本身不实际等待，不用于证明调度速度。
1040 帧回放摘要、66 张 BMP 与旧版 256 MB 完成基线一致；113 项面板
逐项释放/重载及 324 次面板全屏像素比较通过。


## FLC 播放修正后的补充验证（2026-10-16）

本轮对当前演出保留必要资源，不把 60/16 MiB 或 32 MiB 预算当作硬门槛。
128 MB、无交换 QEMU 的标题、四人新局、双人地图和真实时钟完整开局均完成，
进程最高 VmHWM/ru_maxrss 为 57268 KiB（55.93 MiB），系统可用量最低采样
30124 KiB（29.42 MiB），进程 VmSwap 为 0。

四人开局不注入跳过按键，八段角色 FLC 都从第 0 帧开始，逐帧连续且每步
只解码一帧；没有重绕或缓存淘汰。全部 105 个 FLC、3099 帧顺序解码通过。
同一 QEMU 中，Data[508] 的旧前缀查找参考读 68 项，缓存增量 13244768 bytes，
耗时 1144 ms；目标优先查找读 1 项、194776 bytes，耗时 16 ms。两次之间
归还资源 lease，没有清空 OS 文件缓存；这是单项查找参考，不是整机提速测量。

完整结果与受测二进制／安装包哈希保存在
`build/miyoo/flc-playback-validation.json`；新版本实机峰值和音频驱动延迟仍需
安装新包后复测，不能把 QEMU dummy 驱动的耗时换算为实机帧率。
