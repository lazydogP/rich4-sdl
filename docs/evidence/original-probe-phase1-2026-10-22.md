# 原版 hook 第一阶段：运行验证与 DxWnd 拖慢定位

2026-10-22，在本机 Windows 上运行原版 EXE、DxWnd 2.05.68 与 x86 观测探针。工具、参数、格式及边界见 [README](../../tools/frame_diff/README.md)，原设计见 [逐帧比较方案](../original-sdl-differential-testing.md)。可追溯的摘要和输入/输出哈希见 [测量 JSON](original-probe-phase1-2026-10-22.json)。运行原件位于仓库忽略目录 `.local/frame-diff-runs/`，未将游戏资源或截图纳入源码。

## 已实现与实际验证

实现独立启动器、原版 API/内部函数 hook、共享 vtable hook、异步事件及像素写入、PNG/HTML 报告和重复对照汇总。原版实际经过主菜单、选项、新局设置、角色选择、开场动画并进入地图。观察保留原生时钟、种子和线程调度；未实现 SDL 适配、虚拟时钟或逻辑帧锁步。

最终 `game-full-final` 运行 40 秒，使用 renderer=5、`capture full`：

| 项目 | 结果 |
| --- | --- |
| 启动/停止 | 成功，probe_stop=0，存在 END |
| 像素观测 | 594 个原始文件，与 594 个 frame 事件逐一对应 |
| RNG | 95 次调用，返回值、状态转换和线程内连续性全部通过 |
| 原版 Lock/Unlock | 各 1010 次 |
| 图形 HRESULT 失败 / coverage error / 队列丢失 | 均为 0 |
| 最后画面 | 约 39.992 秒，已进入地图，日期面板为 2010 年 1 月 1 日 |
| 完整性状态 | OBSERVED；不是双端等价性结论 |

本次 frame 内存复制合计约 30ms，主线程单次均值 0.050ms、最大 0.479ms。这个数字不包含全部源表面 Lock/Unlock、写盘和日志开销，不能当作整个探针的总成本。

## 可重复的额外开销：DxWnd 绘制后端

四次运行采用同一探针二进制、同一初始资源哈希、同一输入脚本，`capture none`，每次 16 秒。顺序为 renderer 3、5、5、3；采样窗口是探针启动后的 10–16 秒，全部已进入新局设置。每项每次均有 55 个样本。以下为单次调用平均耗时（毫秒）：

| 运行 | renderer | 新局 BltFast，RVA 5C2B | 光标移除 Unlock，RVA 2348 | 光标重画 Unlock，RVA 244C |
| --- | ---: | ---: | ---: | ---: |
| ab-r3-01 | 3 | 3.268 | 2.737 | 3.648 |
| ab-r5-01 | 5 | 0.534 | 0.464 | 0.604 |
| ab-r5-02 | 5 | 0.512 | 0.451 | 0.582 |
| ab-r3-02 | 3 | 2.673 | 2.580 | 3.575 |

跨两次等样本运行，主 BltFast 均值由 2.970ms 降为 0.523ms，约 5.7 倍；三项调用均值合计由 9.250ms 降为 1.573ms。这里是同线程绘制链的 API 成本，**不是整场游戏或帧率提升 5.7 倍**。

已复现的额外开销定位在 DxWnd 的主表面绘制/提交路径。配置中 renderer=3 对应本地帮助的 Primary Surface，renderer=5 对应 GDI；改变这一项就稳定降低了 BltFast 和主表面 Unlock 的成本。GDI 可作为当前采集运行的配置选择；没有改写用户原来的 DxWnd 配置，也没有证据说明必须换后端才能保证原版游戏逻辑正确。

尚未采集 DxWnd/驱动内部调用栈，无法进一步把这部分时间严格拆成颜色转换、窗口提交、驱动等待或桌面合成。上述结论限于这台机器、该二进制版本和已测试场景，不代表所有拖慢都已归因。

## 与拖慢区分开的现象

**原版有意的计时。** IDA 的 `0x404E44` 新局窗口处理函数在调用点 `0x404FA3` 请求 `SetTimer(...,100,NULL)`（返回点 `0x404FAA`）；角色选择后的阶段在 `0x405CEC` 改为 50ms（返回点 `0x405CF3`）。最终运行分别记录到了 100ms 和 50ms。光标 `0x4020FA` 则通过 `timeSetEvent(20,5,0x401F98,...,TIME_PERIODIC)` 独立更新。这些不是 60Hz 主循环。

四次 setup 对照中，取出的 WM_TIMER 平均间隔为 109.386、109.871、109.508、109.517ms，几乎不随 renderer 改变。Windows 实际派发与请求间隔存在偏差；不能把这里约 9–10Hz 的更新节奏直接解释为 renderer 导致的成倍变慢。记录的是 PeekMessage 取出消息的时间，未声称测到了完整消息处理耗时。

**主表面竞争。** `ab-r3-01` 在约 9.049 秒、返回点 `0x40244C` 的 Unlock 出现一次 `0x887601AE / DDERR_SURFACEBUSY`。该运行没有截图读回，因此不能只归因于画面采集；原版主线程与 20ms 光标回调确实都操作主表面。整个运行标记 INVALID_CAPTURE，仍保留计时数据；错误在 10–16 秒统计窗口之外。另一次 renderer=3 和两次 renderer=5 对照未出现该错误。它是间歇性竞争的证据，尚不能证明没有探针时也必现，或证明 GDI 已消除竞争。

**配置中的 slowratio。** 源配置 `slowratio0=2` 本身不表示正在二倍拖慢。已检查的 SLOWDOWN、LIMITFPS、TIMESTRETCH、CPUSLOWDOWN 开关没有启用，`maxfps0=0`、`initts0=0`。这些位的说明参考 DxWnd 头文件和本地帮助；没有用仅看 slowratio 的方式下结论。当前动态对照同样没有呈现二倍计时伸缩。

## 验证与限制

`python scripts/make_minimal.py frame-diff test-frame-diff` 通过。10 个自动化测试覆盖 RGB565/补丁坐标、坏 mask、截断/缺失帧、孤立/越界补丁、缺失 END/丢事件/Unlock 失败、RNG 状态/返回值、零耗时和 p95、抽样预览标记、运行配置隔离。原版 RNG 入口和补丁 ABI 还通过实际游戏的 95 次记录校验；等待函数 hook 已安装，但本次最终场景没有形成 wait 事件，不能宣称这部分已完成动态覆盖。

像素记录发生在表面操作边界，可能包含同一逻辑帧中的中间状态；原版与 SDL 的逐帧对齐仍是后续阶段。样本中成功捕获地图不代表所有窗口、色键 blit、视频路径和表面接口都已支持。
